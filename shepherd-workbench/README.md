# shepherd-workbench

Human review and decision of USCIS benefit requests, with a workbench at `/`.

- Receipting: reviewers verify flagged handwritten values, correct any value, or enter a form entirely by hand.
- Cases: one per benefit request (receipt number). Officers find cases through search, review the filing and evidence, edit case data, assess eligibility criteria, issue requests for evidence, and approve, deny, record a withdrawal or close administratively.
- Workloads: managers register workers with skills and a maximum load, and define rules that assign cases automatically. Workers request cases be added to or removed from their workload.

- Correspondence: letters generated by shepherd-notification are listed on the case and recorded in its history.
- Findings: shepherd-inference findings are listed on the case, reviewed by its assignee, and block approval until resolved or dismissed.

- Input: the durable consumer `workbench-receipting` on `shepherd.intake.recognition.completed.*`. A task is opened when a recognition has fields requiring receipting, or when the document matched no template and carries no `receipt_number` label. A newer recognition of the same document refreshes its active task. There is at most one open or in-progress task per document. The same consumer links documents to cases (see Cases). The durable consumer `workbench-correspondence` on `shepherd.notification.>` records letter generation, holds, deliveries and terminal delivery failures in the case history (deduplicated by event id).
- Output: `receipting.form.v1`, `workbench.case.v1`, `workbench.notice.v1` and `workbench.decision.v1` stored in storage as derived artifacts. Events: `shepherd.workbench.receipting.{required,completed}`, `shepherd.workbench.case.{opened,assigned,decided,reopened}` and `shepherd.workbench.notice.{issued,extended,rescinded}`. shepherd-notification sends no letter for an extension or rescission. Case events use the case's primary document as the subject.

## Receipting modes

| Mode | Fields sent | Result |
|---|---|---|
| `review` | Only fields the reviewer touched. Every flagged field must be included; `null` confirms a blank. | Untouched machine values are kept (`provenance: machine`). A touched value equal to the machine reading is `confirmed`, and anything else is `human`. |
| `full` | Every template field (`null` = blank). | All values `human`; machine values are not used. |
| `amend` | Corrections to a stored receipt, or to a recognition that needed no receipting, through the case (`POST /v1/cases/{id}/documents/{doc}/amend`). A reason is required. | Changed fields become `human`; others keep their provenance. Recorded as a completed task of kind `amend`. The receipt carries `amends` (previous receipt artifact) and `amendment_reason`. |

Tasks record the template (edition) id in `form_type`; `POST`/`PATCH` accept a template id or a form type (its newest edition). Receipts record the form type in `form_type` and the edition in `template_id` (absent in older receipts, where `form_type` is the template id). Values are validated with the template's value types, and failures return 422 with per-field messages. Tasks for unrecognized documents need a form type (`PATCH /v1/tasks/{id}`). Recognition can be re-run with that type (`POST /v1/tasks/{id}/recognize`, proxied to intake). Any stored document can be receipted manually with `POST /v1/tasks`.

`receipting.form.v1`:

```json
{
  "schema": "receipting.form.v1", "document_id": "…", "task_id": "…",
  "form_type": "uscis.i-765", "template_id": "uscis.i-765", "form_number": "I-765", "edition": "08/21/25",
  "mode": "review", "receipted_by": "ana", "receipted_at": "…",
  "source_artifact_id": "…", "form_artifact_id": "…",
  "fields": [{ "id": "…", "label": "20.B. Passport Number…", "value": "C4839201", "provenance": "human",
               "machine_value": "CH839201", "machine_status": "requires_receipting", "machine_confidence": 0.87, "changed": true }],
  "values": { "<field id>": "<final value>" },
  "stats": { "total": 145, "filled": 15, "machine": 8, "confirmed": 4, "human": 3, "changed": 2 }
}
```

## Cases

A case is one benefit request: a primary benefit form plus supporting evidence, identified by a receipt number (`AAA` + 10 digits).

Benefits are defined in `config/benefits.toml` and validated against every edition of each form type at startup. Facts are read through the edition the values were recorded with; a fact may list candidate field ids per edition. Each entry lists the form type, the fields that supply case facts (applicant and beneficiary name, A-Number, date of birth, and the applicant's mailing address as `mailing_*`), form values highlighted on the overview, and the eligibility criteria the officer assesses. The file also lists the denial grounds, and the e-notification form (G-1145) whose e-mail address and mobile number are shown on the case (`e_notification`, from the most recently added case document of that form type). I-765, I-130 and I-90 are configured.

### Opening and linking

On `recognition.completed` for a document in no case:

| Condition | Action |
|---|---|
| `receipt_number` label naming an existing case | Attached as `supporting`. While a notice is outstanding it is attached as `response`, the notice is closed and the case returns to review. |
| Benefit form | Case opened. The receipt number is the label, or `RECEIPT_PREFIX` + 2-digit year + 8-digit sequence. The received date is the `received_date` label, or the upload date. |
| Otherwise | Nothing; the document can be attached or opened as a case manually. |

A receipt for a benefit form in no case also opens one. Intake accepts `receipt_number` and `received_date` on upload and stores them as labels.

Case facts are derived from the primary document's latest receipt, or from its recognition until it is receipted. Facts edited by an officer (`PATCH`) are listed in `overridden` and are not re-derived until reset. Letters are addressed from the `mailing_*` facts; editing them releases a letter held for an incomplete address (retry from the case).

### Lifecycle

| Status | Meaning |
|---|---|
| `open` | Unassigned. |
| `in_review` | Assigned to an officer. |
| `awaiting_response` | Request for evidence (`rfe`, default 87 days) or notice of intent to deny (`noid`, default 33 days) outstanding. |
| `decided` | `decision` is `approved`, `denied`, `withdrawn` or `closed` (administrative closure). |

- An assigned case can be edited only by its assignee: facts, form values, attaching and removing documents, and recording a notice response. A decided case accepts no document changes until reopened; labeled uploads are still attached by the consumer. Assessment, notices and decisions require the requesting user to be the assignee, skilled for the case's form type. Assignment is described under Workloads.
- Criteria are recorded as `met`, `not_met` (a note is required) or `na` (only for `required = false`).
- A form type change (case edit, or a receipt of the primary document as another benefit form) clears all criterion assessments; they are kept in the history event (`criteria_cleared`). An assignee not skilled for the new form type is unassigned (`via: form_type`), and the case is dispatched under the new form type's rules.
- Approval requires: no open receipting tasks on case documents, final values for the primary form (a receipt, or a recognition with nothing flagged), every criterion `met`, or `na` where allowed, and no open inference finding that is unreviewed or `confirmed` (see Findings).
- An outstanding notice is closed by a response or a rescission. The assignee may extend its due date (also after it has passed) to a later date after today, with a reason; the first extension keeps the issued date as `original_due_date`. Rescinding (issued in error, wrong party) requires a reason of 20 or more characters and returns the case to `in_review`. Rescinded notices do not support denial for `abandonment`.
- Denial requires at least one ground and a rationale of 20 or more characters. Unless the ground is `abandonment`, receipting must be complete. While a notice is outstanding, only withdrawal, or denial for `abandonment` after the due date, is possible.
- Withdrawal requires a rationale.
- Administrative closure (`closed`) ends a case without a decision on the merits: `closure_reason` `duplicate`, `opened_in_error`, `transferred` or `other`, and a rationale of 20 or more characters. No receipting, criteria or findings requirement; allowed while a notice is outstanding. The assignee may close; a manager may close any undecided case, assigned or not. The assignee's capacity is refilled. shepherd-notification sends no letter. Reopening works as for other outcomes.
- The primary document can be replaced by another case document (`POST /v1/cases/{id}/primary`, reason required; unassigned or the assignee). The former primary becomes `supporting`. Facts are re-derived from the new primary's form values, keeping `overridden` facts; without form values the current facts stay until it is receipted. Values for another benefit form change the form type as described above; values for a non-benefit form are rejected. The projection moves to the new primary: the former one gets a `workbench.case.v1` retraction (`{case_id, retracted: true, primary_document_id}`, no indexed fields), and shepherd-inference moves `inference.findings.v1` the same way. Earlier notice and decision artifacts stay on the document they were written to.
- The decision is stored as `workbench.decision.v1` on the primary document: outcome, grounds, rationale, criteria at decision time, facts, documents, notices, open findings with their reviews (`findings`, absent without inference), the form artifact relied on, `closure_reason` for a closure, and `supersedes` after a reopening.
- Reopening (motion, service error, supervisory review) requires a reason. The case returns to `in_review` assigned to the requesting user, who must be a worker skilled for the form (capacity is not checked). The previous decision artifact is kept.
- Every action is recorded in the case history, along with free-text notes.

### Workloads

Roles come from the `X-Roles` header (comma-separated). `manager` is required to manage workers and rules, assign, unassign, reassign and resolve requests. Anyone with `X-User` can request.

| Concept | |
|---|---|
| Worker | A user who can be assigned cases: `max_cases`, `auto_assign`, and skills (benefit form types). Load = undecided cases assigned (`in_review` and `awaiting_response`). |
| Skill | Required for every assignment, manual or automatic, and for deciding. A skill cannot be removed while the worker holds undecided cases of that form. |
| Rule | Benefit form type, optional worker pool (empty = every skilled worker), priority (lower first), enabled. |
| Request | A worker's `add` or `remove` request for one case: `pending` → `approved`, `denied`, `withdrawn` (by the requester) or `cancelled` (case decided, worker removed). One pending request per case, worker and kind. |

Automatic assignment applies only to `open` (unassigned) cases whose form type has an enabled rule:

- Dispatch: the rules for the form type are tried in priority order. Eligible workers are in the rule's pool, skilled, `auto_assign`, below `max_cases` and not excluded from the case. The case goes to the one with the lowest load relative to `max_cases`; ties go to the worker assigned least recently, then by name.
- Triggers: a case is opened; a case returns to the pool (unassign, approved removal); the form type changes. A periodic sweep (`WORKLOAD_SWEEP_SECS`) and `POST /v1/workload/sweep` dispatch the whole backlog, oldest received first. Creating or changing a rule starts a sweep.
- Refill: when a worker decides a case, when a case is taken from them, or when their settings change, they receive backlog cases (rule priority, then oldest received) until they reach `max_cases`. A worker at or over `max_cases` receives nothing.
- Exclusion: a worker whose case is returned to the pool (approved removal, manager unassign) is not assigned that case again by rules. A manager can still assign it to them.

Manual assignment by a manager (`assign`, `reassign`, approving an `add` request) requires the skill and refuses a worker at `max_cases` with 409 `over_capacity` unless `force` is set. Reassigning takes the case from its current assignee. Approving `add` for a case held by someone else reassigns it; approving `remove` returns it to the pool. A request that no longer applies (case decided, no longer assigned to the requester) cannot be approved.

Every assignment change is logged in the case history (`assigned` / `unassigned` with `via`: `rule`, `manager`, `request`, `reopen`, `form_type`; `rule_id` or `request_id`) and published as `shepherd.workbench.case.assigned` (`assignee`, `previous`, `assigned_by`, `via`, `rule_id`). Assignment changes are serialized by a Postgres advisory lock, so concurrent dispatch cannot exceed a worker's capacity.

### Findings

With `INFERENCE_URL` set, the case lists its open shepherd-inference findings (rule, severity, summary, the parties involved with links to their cases, review).

- The assignee reviews a finding: `confirmed` (a real conflict), `dismissed` (note required, e.g. a name change) or cleared. Reviews are proxied to shepherd-inference and logged in the case history (`finding_reviewed`). shepherd-inference clears a review when the related cases change.
- A finding resolves when the data no longer matches the rule, e.g. after correcting a misread A-Number or name.
- Approval is refused (422, field `findings`) while a finding is open and not dismissed, and fails with 502 when shepherd-inference is unavailable. Denial and withdrawal are not blocked; findings are recorded with them when they can be read.
- Findings are read at decision time; one raised between that read and the commit is not seen.

### Discovery

`POST /v1/cases/search` sends the query to shepherd-search. `workbench.case.v1` is indexed on the primary document (`shepherd-search/config/mapping.toml`): receipt number, benefit and party names and A-Numbers are content, `status` and `received_at` are columns, and `case_status`, `benefit` and `decision` are facets.

- `scope: cases` matches case records. `scope: documents` also matches the text and form values of every document. Hits resolve to their case through `case_documents`, and documents in no case are returned separately.
- Filters: `status` (any of), `form_type`, `decision`, `received_from`, `received_to`. Sort: `relevance`, `received_at` or `updated_at`. Pagination uses the search cursor.
- A query that is a receipt number or an A-Number is also looked up exactly in the database (`exact`).
- Without `SEARCH_URL`, or when search is unavailable, a database substring match on receipt number and names is returned (`source: database`).

The projection is written after each change to projected state (`cases.revision`). A loop every `CASE_SYNC_SECS` retries cases whose `indexed_revision` trails, so discovery lags a failed write rather than missing it. Assessment changes are not projected.

## Workbench

Usage with screenshots: [docs/ui-guide.md](docs/ui-guide.md).

Cases:
- Worklist: my cases, unassigned, in review, awaiting response, decided, all; filterable by benefit.
- Search: free text, receipt number or A-Number, status, benefit, decision and received-date filters, and facet counts. Documents in no case can be opened as a case.
- Case view: document viewer with receipted or machine-read values overlaid; tabs for overview (case data, applicant facts, e-notification contact, mailing address, form highlights, findings with review, documents, notices, correspondence with letter PDFs, delivery status and retry of held letters), form values (correction with a reason), assessment, decision (readiness checks, approve, RFE/NOID, deny, withdraw) and timeline (history and notes). A banner lists open findings that block approval. Receipting started from a case returns to it.

Receipting:

- Queue: open and in-progress tasks, oldest first, filterable by form type, with completed and cancelled tabs.
- Page view: the scanned page is shown with every field box overlaid and aligned using the recognition's page shift. Box colors: red requires receipting, green resolved, amber changed from the machine value, blue machine-read. Pages with open flags are marked in the page bar.
- Field panel: groups by page and section, and filters by flagged, filled, empty and all. Each flagged field shows the machine reading, its confidence and the reasons, with **Accept** (confirm the reading), **Blank** and **Undo** actions. Enter confirms a field and jumps to the next flagged one. Clicking a box selects its field, and focusing a field scrolls to its box.
- Full manual receipting: selected from the mode menu. All fields are entered by hand, with a progress count.
- Drafts autosave (`PUT /v1/tasks/{id}/draft`). Opening a task claims it. A second reviewer gets a read-only view until the claim is released or goes stale (`CLAIM_TTL_MINUTES`).

Reviewer identity comes from the `X-User` header and roles from `X-Roles`; the page asks for a name once and has a manager toggle. There is no authentication in this service, so deploy it behind an auth proxy that sets `X-User` and `X-Roles` and strips them from client requests.

## Tests

- `cargo test -p shepherd-workbench`: receipt resolution and amendment, case rules, benefit config, discovery request building, workload validation and worker selection.
- `cargo test -p shepherd-workbench -- --ignored cases`: case lifecycle end to end (Docker, vendored pdfium).
- `cargo test -p shepherd-workbench -- --ignored workload`: rule assignment, capacity, requests, reassignment and refill (Docker, vendored pdfium).
- `cargo test --release -p shepherd-workbench -- --ignored scan_to_receipt`: receipting end to end (Docker, vendored pdfium and TrOCR).
